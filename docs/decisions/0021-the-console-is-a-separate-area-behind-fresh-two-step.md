# 0021 · The console is a separate area on the same origin, behind fresh two-step

- **Date:** 2026-11-26
- **Status:** accepted (owner, 26 Nov 2026, with the admin-console plan). Amends the trust model in 0015.

## Context
Vento super-admins changed releases, plans, trials, add-ons, overrides and super-admins through commands on the API host, attributed by a typed `--by` email (decision 0015's trust model): anyone with a shell could type any super-admin's address, and a kill switch needed a laptop and host access. The owner approved a web console (docs/specs/admin-console.md) at app.ventoerp.com/console, on the web app's own origin so passkeys work there (decision 0019 binds them to that host), with its own shell, fresh two-step to enter, and the commands kept only for when the console is down.

## Decision
- **A separate area on the same origin.** The console is its own route tree (`/console`, a root-level route, not under the customer `_app` layout) in the same web app, and its own contract (`@vento/shared/console`, a package subpath never exported from the package root) implemented as `router.console` on the same `/rpc` handler. Every console procedure is built on its own chain (session, then an active super-admin with two-step on, then an open console window, then platform-error mapping), never on `member`; it carries no organization from the session, ignores the tab-organization header, and names an organization only by ID in its input. Every console procedure is declared with `area: 'console'`, and walk tests check both directions.
- **It doesn't exist for anyone else.** To anyone who isn't an active super-admin every console procedure answers NOT_FOUND with no data (anonymous callers get UNAUTHORIZED, like every signed-in procedure, so a super-admin whose session ended sees *Session expired*). The web shows `/console` as the standalone 404 from a `beforeLoad` that imports only the `me` query, so the console's code is never downloaded; the bundle check forbids console paths in the customer entry.
- **Fresh two-step to enter.** Entering needs a passkey, an authenticator code or a backup code proven within the last 5 minutes (`sessions.second_factor_at`, stamped only after a verified passkey, code or backup code, never by a password). The window lives on the session (`console_opened_at`, `console_active_at`) and closes after 15 minutes without console activity or 8 hours after it opened; revoking a super-admin clears it on all their sessions, and a password change carries the second-factor time but not the window. A passkey proof is verified in place with the WebAuthn library the passkey plugin uses (`@simplewebauthn/server`, same version and the same rpID and origin from one settings file), so no new session is made.
- **Same operations, same trail.** Console changes call the same platform operations as the commands, with the same `preview*` lines, the before-state they were previewed against (checked under the operation's lock; a mismatch is refused naming who changed it), and an idempotency key (one platform audit row per key, so a retry returns the first answer and never applies twice). The actor comes from the session; the platform trail records channel `console` and an operator of "console · {browser on device} · {masked IP}". Operation messages never name command flags; each channel adds its own next step.
- **Commands are break-glass.** Change commands refuse unless run with `--break-glass` ("Make this change in the Vento console. If the console is down, add --break-glass."), checked before `--by` and `--reason`. With it they run as before, tagged channel `command`, and every other active super-admin is emailed after the change commits. A registry maps every change command to its console procedure (`apps/api/src/platform/cli/change-commands.ts`); `authorise` takes a registry id, and a parity test runs both channels and compares the audit rows. Read commands, `plans bootstrap` and `superadmin grant --bootstrap` on an empty environment, and the scheduled `plans notify-trials` (channel `scheduled`) are unchanged.

## Consequences
- Every platform change is tied to a real two-step sign-in; `--by` remains only for break-glass, with the other super-admins told at once.
- One deploy and one origin; passkeys work without a new relying-party decision. Customers never download console code (enforced by the bundle check and an e2e test).
- Each console request writes one session row (activity), which is cheap at staff volume.
- New console procedures must use the console builder; walk tests fail otherwise. A new change command must be in the registry with a console equivalent, or it can't be authorised.
- Super-admins can't turn two-step off (My security says "Required because you're a Vento super-admin").
- A password can never mint a fresh factor: for a super-admin, new backup codes and new passkeys need a code or passkey proven in the last 5 minutes, codes or passkeys made without one can't open the console, an authenticator code works once, and customer owners can't reset a super-admin's two-step (security audit, 26 Nov 2026).
- Browser calls to `/rpc` from another origin are refused (Origin / Sec-Fetch-Site check), so a sibling subdomain can't drive console changes.
- A super-admin with no organization lands on the console after sign-in and can use it, but can't manage passkeys until they join an organization (My security lives in a workspace). Follow-up.
- Pre-console platform audit rows keep `channel` null and are labelled at read time; the append-only table is never backfilled.

## Alternatives considered
- A separate host name (admin.ventoerp.com): a second deploy, and passkeys would need a new relying party or related origins; rejected by the owner.
- Putting the console inside the customer shell behind a role: mixes Vento staff power with customer workspaces and their tab guard, and ships staff code to customers.
- A per-action code instead of a window: safer per click but kills the 4-tap kill switch; confirmation dialogs with a reason are the per-action safeguard.
- Re-proving a passkey through the plugin's sign-in endpoint: always creates a new session, rotating the cookie under every open tab and adding a phantom device; verified in place instead.
- A `console_grants` table: gives a history of windows, but the account trail already records each opening (`console.opened`), and columns on the session end with it at sign-out.
