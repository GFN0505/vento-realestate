# Architecture

How the code is laid out and how a request flows through it. The *why* behind the big choices is in `docs/decisions/`. Keep this file current when the structure changes.

## Layout
```
apps/
  api/                     Hono + oRPC server (Node 24)
    src/
      index.ts             starts the HTTP server, graceful shutdown
      app.ts               createApp({ db, mailer?, auth? }): middleware, /health, /api/auth/*, /rpc
      env.ts               zod-validated environment, fails fast on startup
      context.ts           BaseContext every procedure receives (db, headers, auth, mailer)
      orpc.ts              os = implement(contract); authed, member, memberPendingTwoStep builders
      access/              session → membership, tab guard, feature gate, requirePermission, requireAllEntities, who-can-grant,
                           entity scope, system roles,
                           manage-rules.ts (who may manage whom on Team, with the permission ceiling: one source for the
                           services and team.list's flags), role-refusals.ts (who may make, edit, delete, duplicate and give
                           which role: one source for the roles service and roles.list's flags),
                           grants.ts (which entities a granter may give), new-owner-alerts.ts
      platform/            feature flags and plans: availability resolver, in-memory snapshot store, plan limits,
                           operations (stage, group, overrides, plans, trials, add-ons), cli/ (pnpm flags|plans|superadmin)
      auth/                createAuth (Better Auth), hooks, session and password policy, security store
      email/               Mailer (returns a SendResult per message), dev and memory transports, templates
      router.ts            combines module routers
      db/
        client.ts          pg Pool + Drizzle (snake_case columns); DbOrTx type
        columns.ts         id (uuid, Postgres uuidv7()), timestamps
        schema/            one file per module's tables, re-exported from index.ts
        migrate.ts         applies migrations (a release step, never on app start)
        seed.ts            demo data (pnpm db:seed, development only)
      lib/                 logger, request scope (AsyncLocalStorage), client IP, errors, pagination
      modules/<module>/    <module>.service.ts, <module>.router.ts, <module>.test.ts
      test/                env setup, global setup, factories, rollback helper, HTTP and router clients
    drizzle/               generated SQL migrations (committed)
  web/                     Vite + React 19 SPA
    src/
      main.tsx             QueryClient + router
      router.tsx           router instance, typed context
      routes/              file-based routes (TanStack Router); routeTree.gen.ts is generated
      components/          shared UI
      lib/orpc.ts          typed API client + TanStack Query helpers
    e2e/                   Playwright journeys (one spec per journey in docs/journeys)
packages/
  shared/                  zod schemas and oRPC contracts: the single source of API types
    src/
      common/              id, money, currency, isoDate, pagination, Decimal, error map, ORGANIZATION_HEADER, errorReference, joinNames
      <module>/contract.ts contract per module, combined in contract.ts
```

## A request, end to end
1. A component calls `useQuery(orpc.account.me.queryOptions())`. The client and its types come from the shared contract, so a mismatch is a compile error.
2. The browser sends `POST /rpc/account/me` to its own origin with its session cookie. In development Vite proxies `/rpc` and `/api` to the API on port 3000; in production web and API share one domain ([decision 0009](decisions/0009-same-origin-web-and-api.md)).
3. Hono adds a request id (always generated by the server; a client-sent `X-Request-Id` is ignored and ours is returned in that header), security headers and compression, then a **request scope** (AsyncLocalStorage): request id, client IP (socket, or `TRUSTED_IP_HEADER` behind a proxy), masked IP and device. Audit rows and Better Auth hooks read it.
4. oRPC runs the procedure's middleware chain:
   - **`authed`**: Better Auth looks up the session from the cookie (cookie cache off, so a revoked session fails at once), then `enforceSessionPolicy` applies the 30-minute idle and 12-hour limits (deleting an expired session) and records activity at most once a minute. No session → `UNAUTHORIZED {reason: signed_out | session_expired}`.
   - **`member`**: first the **tab guard** ([decision 0013](decisions/0013-tab-organization-guard.md)): the web sends the organization its tab is showing in `x-vento-organization` (`ORGANIZATION_HEADER`). A malformed value, or one that differs from the session's organization, is refused with `CONFLICT organization_changed` before any query; one that differs from the membership actually loaded (removed elsewhere) is refused before the session is written back. No header means no check (scripts, tests). The organization still comes only from the session. `account.*`, `invitations.accept` and `onboarding.createOrganization` are personal and skip it; the guard-walk test in `test/procedure-guard.test.ts` lists them and fails for any other procedure not built on `member`. Then it loads the membership in one query (organization from the session, falling back to the latest membership; role, permissions and entity limits, plus the organization's release group and plan version through a left join on `organization_plans`). Never cached, so access changes apply on the next request. If the role requires two-step (or it was reset) and it's off → `FORBIDDEN two_step_setup_required`. `memberPendingTwoStep` skips that check, for onboarding only. Then the **feature gate** ([decision 0016](decisions/0016-feature-availability-declared-in-the-contract-enforced-in-me.md)): every contract procedure declares `meta.feature` (`platform` = no flag, `forFeature('sales')` = gated); when the feature isn't available to the organization (released and entitled, with prerequisites) the answer is plain `NOT_FOUND`, before any permission check. No query: availability comes from an in-memory snapshot each API server reloads every `FEATURE_SNAPSHOT_REFRESH_SECONDS` (10 s); expiry is compared at read time. The walk in `test/procedure-guard.test.ts` fails if a procedure doesn't declare its feature. Last, it records `members.last_active_at` at most once an hour (a conditional update decided from the value read with the membership, so a recent one costs nothing); `account.me` does the same.
   - **`requirePermission(module, action, doing)`**: refuses with "Only owners and admins can invite people. Ask Olumide Bankole (owner)."
   - **`requireAllEntities()`** (after `requirePermission`, on organization-wide changes: the organization profile, adding, archiving and restoring companies, making, editing and deleting roles, the checklist's one-company answer): a member limited to some entities gets `FORBIDDEN all_entities_required` ("Only people with access to every company can change this. Ask Olumide Bankole (owner)."). The owner's name is read only on refusal.
5. The service receives a `ServiceContext` (organization, member, user: never from input), filters every query by organization and entity limits (`entityScope`), writes in one transaction with `recordAudit` inside it, and returns. Emails are sent by the router after commit with `sendAll`, which never throws and returns one `SendResult` per message (`sent` with the provider's id, `skipped`, or `failed` with a kind). Invitations record that result on the row (`modules/invitations/delivery.ts`: `delivery`, `delivery_message_id`); it's a delivery fact, not audited, and only the send that queued the row can settle it.
6. oRPC validates the output and returns JSON. Unexpected errors (anything that isn't an `ORPCError` below 500, including output validation) are turned into `INTERNAL_SERVER_ERROR {reference}` by a client interceptor in `app.ts`. The reference (`ERR-7F3A-1126`: four hex digits of the request id and the Lagos date, `errorReference` in shared) is in the same log line as the request id; database errors are logged by code and constraint only, so query parameters never reach the log. Each request is logged as one JSON line.

### Authentication (`/api/auth/*`)
Better Auth 1.7 ([decision 0010](decisions/0010-better-auth-identity-own-access.md)) serves sign-up, sign-in, email verification, two-step (TOTP and backup codes) and password reset at `/api/auth/*` on the same Hono app. Before handing a request over, our route applies the session policy and replaces the client-IP header with the trusted value. Our hooks add: password rules (length, upper and lower case, a number and a special character), password history, terms version, sign-in locks, verification resend limits, two-step lock alerts, and audit events. Better Auth routes we don't use are switched off (`DISABLED_AUTH_PATHS` in `auth/auth.ts`, each pinned by `disabled-paths.test.ts` to answer 404): passwordless sign-ins that would skip two-step, session and account endpoints that duplicate our audited oRPC procedures (`/list-sessions`, `/revoke-*`, `/update-user`, the passkey plugin's list, update and delete), `/verify-password` and `/two-factor/get-totp-uri` (an uncounted password check that reveals the authenticator secret), and the unused session, account-linking and social routes (`/update-session`, `/list-accounts`, `/unlink-account`, `/account-info`, `/link-social`, `/sign-in/social`, `/get-access-token`, `/refresh-token`). Anything a later brick needs from that list comes back deliberately, with its own guard and test. With a session, `/two-factor/verify-totp` and `/verify-backup-code` only confirm a newly scanned authenticator: once two-step is on they refuse (`TWO_STEP_ALREADY_ON`), so they can't serve as an uncounted code checker. Passkeys (brick 3d, decision 0019) use the plugin's four ceremony routes only; our hooks check availability, "Confirm it's you", the 10-per-person limit, the reset block and remember-me, never create a second session on registration, and report a suspected copy of a key (a valid signature over this request's challenge with a counter that didn't move forward). The database backs this up: the passkeys insert trigger takes a per-person advisory lock (shared with an admin's two-step reset) and refuses an 11th passkey or one added while a reset is pending, and the counter only moves forward. Better Auth's per-IP rate limiter keeps its counters in memory, because its database storage keys rows by the full client IP; that's right for one API instance, and running several needs Redis (Better Auth secondary storage). Our own public-procedure limiter (`lib/rate-limit.ts`) is in memory for the same reason. Lockouts and resend limits are per email, in the database. Organizations, roles, members and invitations are ours, in oRPC.

### Identity tables
`users`, `sessions`, `accounts`, `verifications`, `two_factors`, `passkeys` (Better Auth's, hand-written in `db/schema/auth.ts`) and `auth_attempts`, `sign_in_locks`, `password_histories`, `known_devices` belong to a person, not an organization, so they have no `organization_id`. Every other domain table has one. The active organization is a column on the session.

### Better Auth upgrade checklist
1. Pin the exact version (`better-auth` and `@better-auth/drizzle-adapter`).
2. Generate Better Auth's schema into a scratch file (`npx auth generate`) and diff it against `db/schema/auth.ts`; `auth-schema.test.ts` fails when a column is missing.
3. Read the release notes for changes to: the two-factor cookie and verification lookup, the `reset-password:<token>` identifier, `createVerificationOTP`, the 24-hour "don't remember me" session (sessions longer than 25 h are treated as "Keep me signed in"), session defaults applied on rotation, after-hooks keeping the endpoint's status for a thrown APIError (our after-hooks return a `Response` instead, see `errorResponse` in `auth/hooks/deps.ts`), and `disabledPaths`.
4. Run `pnpm --filter @vento/api test` (the auth flow tests exercise these over HTTP).

## Conventions that the structure enforces
- **Types live in `packages/shared` only.** The API implements the contract; the web app imports types from it. Never redeclare an API type in `apps/web`.
- **Services hold the logic, routers stay thin.** Services take the context first and are tested against real Postgres.
- **Money** uses `money` (a non-negative 2-dp decimal string; `signedMoney` only for adjustments and reversals) and `Decimal` from `@vento/shared`. Never a JS number. `toMoneyString` refuses amounts too large for `numeric(14,2)`.
- **Lists** take `paginationInput` and return `paginated(item)`: `{ items, page, pageSize, total }`.
- **Role rules are shared.** The pure rules for custom roles (`normalisePermissions`, `toggleCell`, `permissionsBeyond`, `roleNeedsTwoStep`, `permissionChanges`) live in `packages/shared/src/access/role-rules.ts`, so the permissions grid and the server can't drift; *who may do what to whom* stays in `apps/api/src/access/manage-rules.ts` and `role-refusals.ts`. The **permission ceiling**: nobody makes, saves, deletes or gives a role with an action they lack, or manages a person or invitation whose role can do more than theirs (`wider_permissions`). A role id that isn't one of the organization's live roles, deleted a moment ago or another organization's, is `role_unavailable` when giving it: one generic answer.
- **The viewer is re-read inside every access write.** The membership loaded at the start of a request can be stale by the time a write runs, so role create, save and delete, member change, remove and two-step reset, and invitation create, resend and withdraw re-read the viewer with `lockViewer` (their member and role rows `for share`) inside the transaction and apply the rules to that. A change to the viewer's own role or access either lands first and is seen, or waits for the write to commit.
- **Permissions are never cached.** `loadMembership` reads role permissions on every request, so a saved role applies on the holder's next click. Any cache added later must key on `roles.version` (bumped on every save, and the optimistic-concurrency check for `roles.update`).
- **Lock order** for access changes: organization → the viewer (member and role `for share`, `lockViewer`) → the target member or invitation → the role being given (`for share`), saved or deleted (`for update`) → plan row (`organization_plans`). Role saves, member changes, removals and two-step resets also take the organization row first, so two people acting on each other are serialised rather than deadlocked; invitation create, resend and withdraw don't, and only ever share-lock other rows' roles. The guard triggers share-lock the role row too. Restoring a company takes organization → entity → plan row.
- **Team** (`modules/team`): `team.list` is one paginated union of members and open invitations (or removed people) with organization-wide counts, entity names limited to the viewer's access, and per-row `can` flags and `readOnly` reasons from `access/manage-rules.ts`; the members and invitations services throw the same rules' refusals. **Setup checklist** (`modules/checklist`): items live in `items.ts` with the feature they belong to; a brick adds its item and the fact it reads there.
- **Raw SQL** (`db.execute`) bypasses Drizzle's column mapping: timestamps come back as strings, so read them through `rawTimestamp` (`db/raw.ts`).
- **Imports** use `@/` inside each app. Named exports, except route files.

## Data
- PostgreSQL 18 (Docker locally: `pnpm db:up`). Three databases: `vento` for development (only what you create, plus `pnpm db:seed` if you run it), `vento_test` for unit and API tests (recreated each run), and `vento_e2e` for browser tests (created and migrated automatically by `pnpm e2e`).
- Drizzle ORM with `pg` (node-postgres). Postgres `numeric` values arrive as strings, which is what money needs.
- Browse the local database: `pnpm db:studio` (Drizzle Studio at https://local.drizzle.studio), or any Postgres client on `localhost:5432` with the credentials in `.env.example`.
- Schema changes: edit `apps/api/src/db/schema/*`, then `pnpm db:generate`, review the SQL, `pnpm db:migrate` (see the `db-migration` skill).
- Ids are `uuid` defaulting to Postgres 18's `uuidv7()`; organization-scoped tables expose `unique (organization_id, id)` and reference each other with composite foreign keys ([decision 0012](decisions/0012-uuidv7-and-same-organization-keys.md)). Production must run Postgres 18+.
- `audit_events` refuses UPDATE, DELETE and TRUNCATE (trigger), and a deferred trigger keeps at least one active owner per organization (migration `0001_access_guards`).
- Custom roles (brick 3c, migrations `0007_roles_and_organization` and `0008_roles_guards`): a deleted custom role that history refers to is kept with `archived_at` (hidden, its name free again: the name index is partial). Three guard triggers back up the services' own locked checks: no active member (`members_role_not_archived`) or pending invitation (`invitations_role_not_archived`) on an archived role, and no archiving a role someone holds (`roles_archive_unheld`). Each raises `check_violation` naming itself in `CONSTRAINT`; `isGuardViolation` in `lib/errors.ts` maps a hit to the same CONFLICT copy, so a raw trigger error never reaches a user.
- A member's entity limit keeps archived entity ids: `loadMembership` never filters limits by status, so a member limited only to archived companies reads as that list ("No company"), never as `null` (all companies).
- Platform configuration has no `organization_id` ([decision 0015](decisions/0015-platform-configuration-lives-outside-organizations.md)): `feature_releases`, `plans`, `plan_versions`, `platform_admins`, `platform_audit_events`. Per-organization rows (`organization_plans`, `organization_add_ons`, `organization_trials`, `organization_overrides`) are scoped as usual. `plan_versions` and `platform_audit_events` refuse UPDATE, DELETE and TRUNCATE (migration `0004_platform_guards`, which also put every organization that existed before it in the `internal` group). Plan limits are checked in the create's transaction under a lock on the organization's `organization_plans` row (`platform/limits.ts`).
- Demo data: `pnpm db:seed` (Vento Homes Ltd, internal on Enterprise, three active companies and the archived Ikoyi Crest SPV Ltd, ten people including an admin limited to Parkview and Bayo Ogunleye on the custom "Site engineer" role, an "Auditor" custom role nobody holds, a removed person, and pending, expired and bounced invitations; Lekki Partners Ltd, standard on Starter; super-admin ada@vento.ng; password from `SEED_PASSWORD`). Development only, idempotent.

## Resilience
- Database pool: 5s connection timeout, 30s statement timeout, and an error listener so a Postgres restart doesn't crash the API.
- Request bodies on `/rpc` are capped at 1 MB.
- Shutdown stops new requests, waits for in-flight ones (up to 10s), then closes the pool.
- Approximate places (decision 0020): the DB-IP file at `GEOIP_DB_PATH` is read once at startup in the background (`preloadPlaces` in `lib/place.ts`); startup never waits for it, sign-ins before it's ready show no place, and a missing or bad file logs `place_lookup_unavailable` once and leaves places off until restart. Sign-in never reads a file.
- Housekeeping in the API process: every 6 hours it deletes `known_devices` rows unseen for 90 days (each sign-in also prunes that person's own).
- Expected errors (validation, not found, forbidden) aren't logged as incidents; real failures are logged with their stack.
- Tests refuse to run unless `TEST_DATABASE_URL` names a database ending in `_test`. Because audit events can't be truncated, the test run drops and recreates the `public` and `drizzle` schemas, then migrates. Service tests run in a rolled-back transaction (`withRollback`); HTTP auth-flow tests commit with unique emails.

## Environment
Every variable is listed in `.env.example` and validated in `apps/api/src/env.ts`. Locally the API reads the repo-root `.env`; in production the host provides variables and no file is read. Tests replace `DATABASE_URL` with `TEST_DATABASE_URL` and use the memory email transport with per-IP limits off. Until an email provider is added, the API refuses to start with `NODE_ENV=production`. `FEATURE_SNAPSHOT_REFRESH_SECONDS` (1–30, default 10) sets how often availability reloads; `SUPPORT_EMAIL` (required in production) and `SUPPORT_WHATSAPP` (optional, E.164) are where owners' **Talk to Vento** goes. If the snapshot can't load at startup (database down, migrations missing) the API logs an error and serves with every feature off until a reload succeeds.

## Build and run
| | Development | Production |
|---|---|---|
| API | `tsx watch` on the TypeScript source | `tsdown` bundles to `apps/api/dist` (shared package inlined), run with `node dist/index.mjs` |
| Web | Vite dev server on :5173 | `vite build` to `apps/web/dist`, static files |
| Migrations | `pnpm db:migrate` | `node dist/db/migrate.mjs` as a release step |
| Flag and plan commands | `pnpm flags …`, `pnpm plans …`, `pnpm superadmin …` | `node dist/platform/cli/main.mjs flags …`; `plans notify-trials` daily at 08:00 Lagos (cron, with `VENTO_CRON=1`). Trust model: a shell plus `DATABASE_URL` on the API host is super-admin power; `--by` is attribution, not authentication, until the R2 console (decision 0015). The operator is recorded from `VENTO_OPERATOR`, `SUDO_USER`, the SSH client, or `os-user@host` |

## Quality gates
- `pnpm check` (Biome), `pnpm typecheck` (TypeScript 7, strict), `pnpm test` (Vitest: shared schemas, API against Postgres, web components), `pnpm e2e` (Playwright, desktop and mobile).
- CI (`.github/workflows/ci.yml`) runs all of them on every pull request, with a Postgres service. In CI, e2e runs against the production builds (`node dist/index.mjs` and `vite preview`), not the dev servers.
